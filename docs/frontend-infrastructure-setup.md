# Infrastructure setup — shopware-fe test storefront (Proxmox LXC)

The `shopware-fe` LXC (Debian Trixie, Node 22, pnpm) runs the legacy
`@shopware-pwa` (Nuxt 2) test storefront against the `shopware-be` plugin
backend. This project (`/var/www` on the CT) is **not** part of this repo —
it is a separate `shopware-pwa-project` scaffold deployed directly on the CT.
This doc only covers the CT-level setup/runbook; the systemd unit below is
also installed live on the CT.

## Root cause of the "No theme found" crash (2026-09-12)

The project's `README.md` documents **yarn** (`yarn install` / `yarn dev`),
but the CT was set up with **pnpm**. pnpm's strict, non-flat `node_modules`
does not hoist transitive dependencies the way yarn does, which broke several
things that "just worked" under yarn:

1. `@shopware-pwa/default-theme` was never a direct dependency (only pulled
   in transitively via `@shopware-pwa/nuxt-module`) → no symlink under
   `node_modules/@shopware-pwa/default-theme` → Nuxt couldn't resolve the
   theme at all (`No theme found for "/var/www/@shopware-pwa/default-theme"`).
   Fixed by adding it explicitly to `dependencies` (pinned to the lockfile's
   `1.6.2`).
2. The project's `package.json` `resolutions` field (yarn-only) pinning
   `vue`/`vue-server-renderer`/`vue-template-compiler` to `2.6.14` was
   silently ignored by pnpm, causing a Vue version-mismatch build failure.
   pnpm's equivalent lives in **`pnpm-workspace.yaml`** (not
   `package.json` — pnpm 10+ moved workspace-level settings there):
   ```yaml
   overrides:
     "@glidejs/glide": 3.5.2
     vue: 2.6.14
     vue-server-renderer: 2.6.14
     vue-template-compiler: 2.6.14
   ```
3. Nuxt 2's own webpack/babel pipeline (`@nuxt/babel-preset-app`, required by
   `.babelrc`-adjacent tooling) also assumes flat hoisting. Rather than
   whack-a-mole individual phantom-dependency fixes, hoisted linking was
   enabled project-wide in `pnpm-workspace.yaml` (pnpm 10+ moved this out of
   `.npmrc` too):
   ```yaml
   nodeLinker: hoisted
   ```

## Required one-time scaffolding (`.shopware-pwa/`)

The `@shopware-pwa/nuxt-module` requires a `.shopware-pwa/` directory
(CMS component map, locale files, plugin-slot components) that is normally
generated by `@shopware-pwa/cli`. It was missing entirely on this CT. It's
regenerated (idempotent, safe to rerun after a theme/package upgrade) via the
CLI, non-interactively:

```bash
cd /var/www
node_modules/@shopware-pwa/cli/bin/shopware-pwa cms
node_modules/@shopware-pwa/cli/bin/shopware-pwa languages
node_modules/@shopware-pwa/cli/bin/shopware-pwa plugins --ci
```

`shopware-pwa domains` (multi-domain routing) additionally needs Shopware
**Admin** credentials (not just the storefront access key) and was not run.
Instead, `.shopware-pwa/sw-plugins/domains.json` was populated by hand from
the public, unauthenticated `GET /store-api/context` response (using the
sales channel's own access key) for the `HeadlessChicken` sales channel /
`http://shopware-fe.lan.internal:3000` domain. If the BE domain, sales
channel, language, or currency changes, either rerun `shopware-pwa domains`
with real admin credentials, or refetch `salesChannel.domains[0]` from
`/store-api/context` and update `domains.json` by hand (schema: see
`toolbox.domains.prepareDomainsMap` in
`node_modules/@shopware-pwa/cli/build/extensions/domains-extension.js`).

**Also required**: `shopwareDomainsAllowList` must be set in
`shopware-pwa.config.js` (see below) — without it, the domain-routing plugin
silently filters `domains.json` down to an empty list and every request
fails with *"There is no domain configuration for ..."*, regardless of what
`domains.json` contains.

## `shopware-pwa.config.js` (not in git — lives only on the CT)

```js
module.exports = {
  shopwareEndpoint: "https://swbe.markusfriedrich.de",
  shopwareAccessToken: "<Storefront API access key of the HeadlessChicken sales channel>",
  shopwareDomainsAllowList: ["http://shopware-fe.lan.internal:3000"],
}
```

This file contains the sales channel's Storefront API access key. It is
**not** checked into version control — set it up manually on the CT (or via
your own secrets tooling) after cloning/redeploying. If the BE moves DNS
names or the access key rotates, update this file and rerun `pnpm nuxt build`
(the build bakes the config into the server bundle).

## `frontends/`, `minimal-fe/`, `shopware-frontend/`

These sibling directories under `/var/www` are unrelated scratch/reference
projects (the official Shopware "Composable Frontends" monorepo clone, and
two Nuxt 3/4 experiments) that happen to live next to the actual
`shopware-pwa-project`. They are excluded from `tsconfig.json`'s `exclude`
list so the Nuxt 2 build's type checker doesn't try to compile them.

## Vimeo CMS element build error

`@shopware-pwa/default-theme`'s `CmsElementVideoVimeo` pulls in
`vue-vimeo-player` / `@vimeo/player`, which ship modern JS syntax that
Nuxt 2's webpack 4 + babel-loader doesn't transpile by default (it excludes
`node_modules`). Fixed with `build.transpile` in `nuxt.config.js`:

```js
build: {
  transpile: ["vue-vimeo-player", "@vimeo/player"],
},
```

## systemd (`/etc/systemd/system/shopware-fe.service`)

Build-then-start mode (no hot reload — rebuild manually after code changes):

```ini
[Unit]
Description=Shopware PWA test frontend (shopware-fe)
After=network.target

[Service]
Type=simple
WorkingDirectory=/var/www
Environment=HOST=0.0.0.0
Environment=PORT=3000
Environment=NODE_ENV=production
ExecStart=/root/.local/share/pnpm/bin/pnpm nuxt start
Restart=always
RestartSec=3
SyslogIdentifier=shopware-fe

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now shopware-fe.service
journalctl -fu shopware-fe
```

After any dependency/theme/code change, rebuild before restarting:

```bash
cd /var/www && pnpm nuxt build && systemctl restart shopware-fe.service
```

## Known follow-up (not a frontend/infra issue)

`GET http://shopware-fe.lan.internal:3000/` currently returns a themed
`404`. The server boots and renders correctly (confirmed via SSR HTML
output with the right theme/assets); this looks like a Shopware-side CMS/
navigation content gap for the `HeadlessChicken` sales channel (e.g. no
Home page assigned) rather than a frontend bug. Worth checking in the
Shopware admin (Sales Channels → HeadlessChicken → Storefront settings).

## Monitoring

- `shopware-fe`: TCP port `3000` on `shopware-fe.lan.internal` (prefer a
  plain TCP check over HTTP-200 here, since a themed `404` on `/` is a valid
  "server is up" response for this test frontend).
- `shopware-be`: Apache now listens on **port 8080**, not 80/443 —
  `http://shopware-be.lan.internal:8080/api/_info/version`
  (a `401` is also a valid "up" response; it only means the endpoint answered).
- `shopware-cqrs` (CQRS read/write-queue Postgres, called
  `order-integration-db` in `docs/infrastructure-setup.md` but actually
  provisioned as `shopware-cqrs.lan.internal`): TCP port `5432`.
